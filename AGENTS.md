# Repository guidance

- Read `README.md` for setup, commands, and the configuration reference, `docs/architecture.md` for design decisions and code responsibilities, and `docs/testing.md` for database, Docker, and cache verification and troubleshooting before changing related areas.
- Keep documentation roles distinct: put quick setup, the configuration table, and the PostgreSQL query in the README, design rationale and layer responsibilities in `docs/architecture.md`, and detailed verification and troubleshooting steps in `docs/testing.md`. Update all three when a change affects setup, architecture, or verification.
- Keep the hexagonal boundaries intact: domain rules stay framework-independent, application code depends on ports, and external tools belong in infrastructure adapters. Inbound adapters depend on input ports such as `GetEntriesPort`, not on concrete use cases. `test/architecture.test.ts` enforces this.
- Mirror `src/` when adding tests under `test/`. Prefer deterministic tests with fixtures and injected clocks over tests that depend on live Hacker News responses or wall-clock delays.
- After code changes, run `pnpm typecheck`, `pnpm test`, `pnpm lint`, and `pnpm build`. Run `pnpm test:coverage` with `TEST_DATABASE_URL` set (or `docker compose run --rm --build test`) when changing behavior or tests; without PostgreSQL the integration tests are skipped and coverage falls below its thresholds.
- Use the Docker Compose stack in `docker-compose.yaml` for a local database: `docker compose up -d postgres` before `pnpm dev`. PostgreSQL integration tests must use `TEST_DATABASE_URL` for a disposable database and create isolated schemas; never point tests at a production database.
- `.env` holds the production `DATABASE_URL` and is read only by `pnpm start`. Do not read, print, edit, or run commands against it unless the user asks. Local work uses `.env.local` (from `.env.local.example`), which `pnpm dev` and `pnpm benchmark` read. Never commit either file.
- Do not run `docker compose down -v` or remove the `postgres-data` volume on a developer's machine without asking, because it deletes their usage history. Use a separate project name (`COMPOSE_PROJECT_NAME`) and other ports for throwaway verification stacks, and remove only what you created.
- Schema changes go in a new numbered migration in `src/infrastructure/database/postgres-usage-repository.ts`; never edit an applied migration.
- Keep versions aligned: the Node version in `.node-version` and the `Dockerfile`, and the PostgreSQL image (`postgres:18-alpine`) in `docker-compose.yaml` and `.github/workflows/ci.yml`.
- Keep changes on the task's branch. Do not create or merge a pull request unless the user asks.
